# Architectural decisions

Newest first. Each entry: decision, then why.

## 2026-10-10 · Phase 2 (Luma integration)

Verified against https://docs.luma.com (changelog through October 2026) and
the published OpenAPI spec (`https://public-api.luma.com/openapi.json`).

**Endpoints: the June 2026 flat-response routes.** `GET /v1/events/get`,
`/v1/events/guests/list`, `/v1/events/guests/get`, `/v1/events/ticket-types/list`
(with `include_hidden=true`), auth via `x-luma-api-key`. The older
`/v1/event/*` routes still work but are deprecated and return nested shapes.

**Check-ins are tracked in our database only.** Luma's API has no endpoint
to set a guest's or ticket's check-in status (`guests/update-status` covers
approved/declined/pending_approval/waitlist only). Luma does expose a
per-ticket `checked_in_at`; we don't import it, so check-ins made in Luma's
own check-in app don't show up here. Easy to add if staff will use both.

**Tickets are keyed by Luma ticket id; ticket keys are learned.** Guest
payloads carry the guest key (inside `check_in_qr_code`) and each ticket's `id`,
but never a ticket key, even though `guests/get` accepts one. So:
`tickets.luma_ticket_id` is the stable key, and `tickets.ticket_key` is
nullable. When a scanned key isn't known locally, `luma-resolve-key` asks Luma
which guest it belongs to, syncs that guest, and stores the key in
`luma_key_aliases` (pinned to a ticket when the guest has exactly one), so the
next scan resolves offline. `resolve_check_in_key()` checks guest key → ticket
key/id → alias.

**Webhook authenticity: URL token + re-fetch, not signatures.** Luma returns
a `secret` when a webhook is created but doesn't document a signing scheme,
so we can't verify signatures. Instead: (1) the webhook URL carries a 32+ char
random `LUMA_WEBHOOK_TOKEN`, compared in constant time; (2) the guest is
re-fetched from the Luma API and that answer is stored, with the payload used
only if Luma is unreachable. A forged request without the token is rejected;
even with it, it can at most trigger a re-fetch of real data. Re-fetching also
makes out-of-order deliveries harmless. If Luma publishes a signing scheme,
add verification in `luma-webhook` alongside the token.

**Internal secrets live in Supabase Vault, generated by the database.** The
webhook URL token and the token pg_cron uses to call `luma-sync` are created on
first use by `internal_secret()` (service role only) and never pass through a
person or the repo. `register_webhook` builds the URL and registers it with Luma
itself. This replaced asking the operator to generate a token and paste it in
two places.

**Both Supabase key formats are supported.** Functions prefer
`SUPABASE_SECRET_KEYS` / `SUPABASE_PUBLISHABLE_KEYS` and fall back to the legacy
`SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_ANON_KEY`, which Supabase retires at the
end of 2026 (around the event dates). Backend callers are recognised by a secret
key in `apikey`, a legacy service JWT, or the Vault cron token.

**Writes to Luma are not retried on 5xx.** Only 429s (rejected before acting)
are retried for POSTs, so a flaky response can't register a webhook twice.

**Webhook de-duplication by body hash.** Luma sends no delivery id, so the
SHA-256 of the raw body is the receipt id. The receipt is deleted if
processing fails so Luma's retry is processed.

**Verified against a real Luma event (2026-10-10).** Linking
`evt-sjZpNrnBWMYQFwm` synced 784 guests / 2,038 tickets in one run. Every
guest key parsed from `check_in_qr_code` (`g-` + 15 chars); ticket ids are
`eventticket-` + 15 chars; guest ids `gst-`. A second full sync rewrote no
rows. The webhook registered and re-registration reported `exists`. Findings
that shape later phases:
- Guests often hold many tickets (up to 24 on one registration), so a guest-key
  scan must let staff check in some or all of a group.
- Luma ticket types include add-ons (e.g. "After Party Upgrade") that are not
  entry tickets. Ticket types need an "admits entry" flag so add-ons are not
  counted as check-ins (Phase 3, with the perks mapping).
- The event's own timezone comes from Luma (this one is America/Toronto), so
  nothing should assume Central time.

**Webhook types handled:** `guest.registered`, `guest.updated` and
`ticket.registered` (all carry the full guest with `event_tickets` and
`event`). Others, including `guest.refunded`, are acknowledged and ignored.

**Upserts happen in SQL.** `luma_upsert_guests` / `luma_upsert_ticket_types` are
service-role-only functions: atomic per batch, tested in the Postgres suite,
shared by sync and webhook. A guest payload is treated as that guest's full
current state: tickets no longer listed become `invalidated` (never deleted, so
check-in history survives) and can be reactivated. Unknown ticket types seen in
a webhook are created from the ticket's type name. Sync only refreshes type
names, so a manager's hide/reorder choices survive. Unchanged rows aren't
rewritten.

**Payment status is ignored.** `is_captured` and all amounts are dropped at the
adapter. A ticket is valid when Luma lists it and the guest is `approved`.

**Backfills are resumable.** `luma-sync` stops starting new pages after
`SYNC_TIME_BUDGET_MS` (default 100s, under the edge function limit), saves the
cursor on the run, and returns `done: false` with the `run_id`; calling again
with that `run_id` continues. One running sync per event (409 otherwise); runs
idle for 5 minutes are treated as abandoned.

**Rate limits.** Luma allows 200 req/min per calendar key and blocks for ~60s
after a 429. The client honours `Retry-After`, paces itself when
`X-RateLimit-Remaining` hits 0, retries 5xx and network errors with
backoff (3 attempts), and gives up rather than wait more than 65s at once.
Errors never include the API key.

**Functions authenticate callers themselves** (`verify_jwt = false`): the
service role key (cron) or a user JWT checked with `my_event_role()`. Luma
can't send a JWT, and this also works with Supabase's newer non-JWT API keys.

**Shared code is vendored into `supabase/functions/_shared/nt`.** Supabase's
bundler doesn't reliably include files outside `supabase/functions`, so
`pnpm functions:vendor` copies `packages/shared/src` there and a test fails if
the copy drifts. `deno check` runs in CI.

## 2026-10-10 · Phase 1 (foundation)

**New repository, separate from agency-os.** Nothing is shared with the
existing agency-os app, and keeping them apart avoids breaking its Vercel
deploy.

**Guest is not a stored role.** A user is a guest for an event when a guest row
for that event is linked to their account. Staff and manager are per-event
(`staff_assignments`). Admin is a global flag on `profiles`. This keeps "who is
a guest" in sync with Luma automatically.

**Tickets are linked by confirmed email, in the database.** A trigger on
`auth.users` links every guest row with a matching email across all events
when the email is confirmed. A trigger on `guests` links rows synced after the
account exists. Changing an account's email unlinks rows that no longer match.
`link_my_guests()` is an idempotent RPC the apps call after sign-in. Unconfirmed
emails never link, so nobody can claim tickets by signing up with someone
else's address.

**Emails are lowercased `text`, not `citext`.** Supabase installs extensions
into the `extensions` schema while plain Postgres uses `public`, which breaks
`search_path = ''` functions. Emails are normalised by trigger and checked by
constraint instead.

**Check-ins and redemptions are append-only and written only through RPCs.**
`record_check_in`, `undo_check_in`, `record_perk_redemption` and `adjust_perk`
are `security definer` functions that check permissions, validate the ticket,
lock the ticket row and write the audit log. Direct INSERT/UPDATE/DELETE on
these tables is revoked from app roles, whatever RLS says.

**Idempotency via client-generated `op_id`.** Every operation carries a UUID
generated on the device. Replaying an op returns the original result without
re-validating, so a retry after success never fails and never double-counts.
Reusing an op_id for a different ticket or perk is an error.

**Conflicts are resolved by derivation, not by stored flags.** The effective
check-in is the earliest non-undone scan by device time, with `op_id` breaking
ties (`ticket_check_in_status` view). Over-limit redemptions are computed by a
running balance in the same order (`perk_redemption_ledger` view). Because
nothing depends on arrival order, every device converges on the same answer
whatever order offline queues sync in. Device clocks ahead of the server are
clamped to server time.

**Offline over-limit redemptions are accepted and flagged** (approved by
product). An offline redemption has already happened at the bar, so rejecting
it at sync would only hide it. Online redemptions past the allowance are
rejected (`perk_exhausted`). The time window is checked against scan time for
both.

**Balances are derived, never stored.** `ticket_perk_balances` = mapped
allowance − sum of redemption quantities. Manager adjustments are ledger rows
with a required reason (negative quantity gives units back).

**Audit log.** RPCs write explicit audit rows (actor, device, reason). Tables
managers edit directly (events, perks, mappings, content, sponsors,
notifications, staff assignments) have a generic audit trigger. `audit_log.event_id`
has no FK so audit rows survive event deletion.

**Composite foreign keys keep data inside one event.** Tickets, mappings and
ledgers reference `(id, event_id)`, so a ticket type, perk or ticket from one
event can never be attached to another event, even by an admin.

**No financial data, enforced three ways.** No such columns exist. Luma zod
schemas strip unknown keys at the adapter boundary. A test fails if any public
column name looks financial (price, amount, currency, fee, …). Webhook bodies
are never stored; `luma_webhook_receipts` holds identifiers only.

**Managers cannot create events or change staff.** Only admins create and
delete events and manage `staff_assignments`. Managers edit their assigned
events, perks, content and notifications. Ticket types, guests and tickets are
written only by the Luma sync (service role); managers may hide or reorder
ticket types.

**Published events are visible to every signed-in user.** Lineup, info and
sponsors are public event content. Drafts are visible only to the event's staff.
Anonymous users see nothing; the apps require sign-in.

**Mock Luma adapter behind one interface.** `LumaAdapter` exposes normalised
types, not raw Luma payloads. `LUMA_MODE=mock` (the default) uses a
deterministic in-memory dataset; `live` arrives in Phase 2. `supabase/seed.sql`
is generated from the same dataset (`pnpm seed:generate`) and a test fails if
it drifts, so the database seed and the mock API always agree.

**Shared code is Deno-compatible.** `packages/shared` uses explicit `.ts`
imports and no Node APIs in `src/`, so Supabase edge functions can import it
directly. Bare `zod` is mapped via the functions' import map.

**RLS tests run on Vitest + `pg`, not pgTAP.** pgTAP isn't installable in the
build environment, and plain TypeScript tests share tooling with the rest of
the repo. A small shim (`supabase/tests/helpers/supabase-shim.sql`) emulates
Supabase's `auth` schema and roles, so tests run on any Postgres 15+ (CI uses a
`postgres:17` service). Each test runs in a rolled-back transaction and
switches role with `set local role` + JWT claims, exactly like PostgREST.

**Generated DB types later.** Hand-written domain types live in
`packages/shared/src/types/domain.ts`. `supabase gen types` output is added
once the Supabase project is linked (Phase 3), when the apps start querying.
